How to use the backend

Questions and answers for every feature of the OCS-in-a-Kit backend. Open a question to read the answer.

Back to the home page

Jump to: Getting started · Accounts · Administration · Web security · Features · Running it

{% call section("start", "Getting started") %} {% call qa("What is this backend?") %}

The service behind your site. It keeps the accounts, signs people in, decides who may do what, and stores the data each feature needs. The pages you open here are for admins; the rest of your site talks to it through the REST API under /api. The home page shows your organization, your kit and what is switched on.

{% endcall %} {% call qa("How do I sign in?") %}

On these pages, use Login. From code, send your username and password:

curl -c jar -X POST {{ api_base }}/api/authenticate \
  -H 'Content-Type: application/json' -H 'X-Origin: client' \
  -d '{"uid": "your-uid", "password": "your-password"}'
curl -b jar {{ api_base }}/api/id

The first call saves a cookie in jar; the second asks who you are. A wrong password answers 401.

{% endcall %} {% call qa("How do I sign out?") %}

On these pages, use Logout in the top-right menu. From code, DELETE /api/authenticate invalidates your token cookie.

{% endcall %} {% call qa("What are the roles?") %}

Every account has one role. Three are built in, and this kit calls them {{ kit.roles.admin.label }} (runs the site and is the only one who can change features, permissions, CORS and roles), {{ kit.roles.staff.label }} (day-to-day work: sections, classrooms, grading, approvals) and {{ kit.roles.member.label }} (a regular user). New sign-ups get {{ kit.roles[kit.signup_role].label }}. {% if kit.custom_roles %}Admins have added {% for role in kit.custom_roles %}{{ role.label }} (L{{ role.tier }}){% if not loop.last %}, {% endif %}{% endfor %}.{% endif %}

Every role has a tier from L1 (strongest) to L4 (weakest) that says how much it may do; the built-in roles start at L1, L2 and L3. A stronger role can do everything a weaker one can.

{% endcall %} {% call qa("How do I switch between light and dark mode?") %}

Use the sun and moon switch at the right of the top bar: switch on is dark, off is light. The first time, the pages follow your computer's setting. After you choose, your browser remembers it, and it applies at once on every page, including the animated background. It is a setting of your own browser, so it does not change anything for other people.

{% endcall %} {% call qa("What makes a good password?") %}

At least 8 characters with an uppercase letter, a lowercase letter, a number and one of ` ~ ! @ # $ % ^ & * ( ). Anything weaker is refused with a 400. Spring and Pages use the same rule.

{% endcall %} {% endcall %} {% call section("accounts", "Accounts and profiles") %} {% call qa("How does someone sign up?") %} 
curl -X POST {{ api_base }}/api/user -H 'Content-Type: application/json' \
  -d '{"name": "Ada Lovelace", "uid": "ada", "password": "Sup3r!secret", "email": "ada@example.org"}'

The account gets the kit's sign-up role. If the admin limited sign-ups to certain email domains (ALLOWED_EMAIL_DOMAINS in .env), other addresses are refused. POST /api/user/guest makes a guest account from just a username and password.

{% endcall %} {% call qa("How do I see and change my own profile?") %}

GET /api/id returns your account. PUT /api/user changes it; send only what changes:

curl -b jar -X PUT {{ api_base }}/api/user -H 'Content-Type: application/json' \
  -d '{"name": "Ada L.", "organization": "Analytical Engines Ltd"}'

You can change name, email, sid, password, organization and class. Only an admin can change another person's account.

{% endcall %} {% call qa("What is the organization field?") %}

The name of the organization an account belongs to. GET or POST /api/organization reads or sets it. Classrooms are visible to people of the same organization. The old names school and /api/school still work, so older sites keep running.

{% endcall %} {% call qa("How do I set a profile picture?") %}

PUT /api/id/pfp with {"pfp": "<base64 image>"} sets it, GET /api/id/pfp returns it, and an admin can remove one with DELETE /api/id/pfp?uid=....

{% endcall %} {% call qa("What are sections, and how do I join one?") %}

Sections are groups, such as a class or a team. An admin creates one:

curl -b jar -X POST {{ api_base }}/api/section -H 'Content-Type: application/json' \
  -d '{"name": "Computer Science A", "abbreviation": "CSA"}'

GET /api/section lists them. A person joins with POST /api/user/section and {"sections": ["CSA"]}, and sees theirs with GET /api/user/section. Admins can browse sections on the Sections page.

{% endcall %} {% call qa("How do classrooms work? (" ~ kit.roles.staff.label ~ ")") %}

A classroom is a named group of people owned by a staff member, tied to their organization.

curl -b jar -X POST {{ api_base }}/api/classrooms/ -H 'Content-Type: application/json' -d '{"name": "Period 1"}'
curl -b jar -X POST {{ api_base }}/api/classrooms/1/students/7      # add the person with id 7
curl -b jar {{ api_base }}/api/classrooms/1/students                 # list them

Staff and admins create, rename, delete and change who is in a classroom; members can read the classrooms of their own organization.

{% endcall %} {% endcall %} {% call section("admin", "Administration (" ~ kit.roles.admin.label ~ ")") %} {% call qa("Where do I manage users?") %}

In the Data menu, open User Management. It lists every account, and an admin can edit, delete or reset the password of any of them. A reset sets the password to the default from .env (DEFAULT_PASSWORD), and the person should change it at once.

{% endcall %} {% call qa("What happens when I delete a user?") %}

An admin cannot delete their own account. A person who still owns records, such as posts or classrooms, is kept and the answer says so (a 409) instead of pretending it worked. Delete or reassign those first.

{% endcall %} {% call qa("How do I turn features on or off, or switch kits?") %}

A kit is a preset list of features: vanilla (accounts only), education and business. GET /api/kit shows what is on. An admin changes it with no restart:

curl -b jar -X PUT {{ api_base }}/api/kit/admin/features -H 'Content-Type: application/json' \
  -d '{"features": {"social": false}}'
curl -b jar -X PUT {{ api_base }}/api/kit/admin/kit -H 'Content-Type: application/json' -d '{"kit": "business"}'

A feature that is off answers 404 and keeps its data. A kit switch never touches accounts. GET /api/kit/admin shows what each feature needs to work.

{% endcall %} {% call qa("How do I back up, move or restore the data?") %}

Admins can download everything with GET /api/export/all, and load it with POST /api/export/import. For a whole database move, use the scripts in scripts/: db_migrate-prod2sqlite.py pulls a server's data into a local file, and db_restore-sqlite2prod.py pushes it back.

Careful: scripts/db_init.py drops every table and rebuilds the database. It asks first, and backs up before it drops.

{% endcall %} {% call qa("How do people send feedback?") %}

POST /api/feedback/ with a title, a body, and optionally a type (Bug, Feature Request, Inquiry or Other) and a uid. It can be anonymous. If a GitHub repository and token are set in .env it also opens an issue. Staff read all feedback with GET /api/feedback/all.

{% endcall %} {% endcall %} {% call section("security", "Web security") %} {% call qa("How do I change who can use something?") %}

In the Data menu, under Web Security, open Permissions. Every request is listed, grouped by feature. Pick a level, press Save, and it applies on the next request:

  • public: anyone, signed in or not
  • {{ kit.roles.member.label }}: any signed-in account
  • {{ kit.roles.staff.label }}: staff and admin
  • {{ kit.roles.admin.label }}: admin only

Rows are green when a level has been decided, yellow when nobody has decided yet (open to anyone until someone does), and red when locked (login and the page itself, so you cannot lock yourself out). Reset goes back to the level in permissions.json. A route with its own check in code keeps that check, so the page can always make something stricter, but can only make it more open where the code has no check of its own.

{% endcall %} {% call qa("What are tiers (L1 to L4), and how do I add a role?") %}

A tier is a role's default permissions: how far up the permission levels it reaches.

  • L1: everything, like the admin role
  • L2: the {{ kit.roles.staff.label }} level (day-to-day work)
  • L3: the {{ kit.roles.member.label }} level (what any signed-in account may do)
  • L4: public level only, no more than someone who is not signed in

In the Data menu, under Web Security, open Roles. Type a name (2 to 20 characters), pick a tier and press Add role. You can also rename any role, change the tier of {{ kit.roles.staff.label }} or {{ kit.roles.member.label }}, and see how many requests each tier may make. The admin role is always L1 and cannot be removed. Everything follows the tier at once: the permission check, the pages and the code that asks whether someone is staff or admin.

A tier is only the starting point. To change what a level may do for one request, use the Permissions page.

{% endcall %} {% call qa("How do I give someone a role?") %}

On the Roles page, use Give an account a role: type the account's uid, pick the role and press Assign. From code: PUT /api/user/role with {"uid": "ada", "role": "Mentor"}. You cannot change your own role, so the admins can never be locked out, and a role that accounts still hold cannot be deleted until they have another.

{% endcall %} {% call qa("I added a route and it answers 403 saying it is not in permissions.json.") %}

A request in no list is refused for everyone, so a new route is never open by accident. Add it to permissions.json under the level that should use it, then run python -m permissions --check.

{% endcall %} {% call qa("My website gets a CORS error in the browser.") %}

Browsers only let a website call this backend if its origin is allowed. In the Data menu, under Web Security, open CORS, type the site's origin, press Add and then Save. It applies on the next request.

An origin is the scheme, host and port with no path and no trailing slash: https://pages.example.org, http://localhost:4500. Anything else is refused with a message saying what to fix. Reset forgets your list so the CORS_ORIGINS setting in .env decides again.

{% endcall %} {% call qa("Who changed a setting, and when?") %}

The Permissions, CORS and Roles pages each end with Recent changes, a log of who changed what. Feature changes are in GET /api/kit/admin under recent_changes.

{% endcall %} {% endcall %}
{% call section("social", "Social: microblogs, posts and personas", "social") %} {% call qa("How do I post a short update (microblog)?") %} 
curl -b jar -X POST {{ api_base }}/api/microblog -H 'Content-Type: application/json' \
  -d '{"content": "Shipped the new login page!", "topicPath": "/blog/login"}'

A post is at most 280 characters. topicPath files it under a page, and the topic is created for you. Read a page's posts with GET /api/microblog/page/<page_key>, reply with POST /api/microblog/reply, and react with POST /api/microblog/reaction. You can change or delete your own posts; admins can change anyone's.

{% endcall %} {% call qa("What are posts, and how are they different?") %}

POST /api/post with {"content": "...", "pageUrl": "...", "pageTitle": "..."} makes a longer post tied to a page, and POST /api/post/reply replies. GET /api/post/all lists them, GET /api/post/page?url=... lists a page's, and GET /api/post/user/<id> lists one person's.

{% endcall %} {% call qa("What are personas?") %}

Descriptions of working styles that people pick to describe themselves. GET /api/persona lists them, and POST /api/user/persona with {"persona_id": 3, "weight": 2} picks one. Admins manage them on the Personas page. Staff can ask POST /api/persona/form-groups to build balanced groups from people's personas.

{% endcall %} {% endcall %} {% call section("ai", "AI chat and grading", "ai-chatbot") %} {% call qa("How do I ask the AI a question?") %}

You need to be signed in, and an admin must have set GEMINI_API_KEY and/or GROQ_API_KEY in .env. Without a key the feature turns itself off.

curl -b jar -X POST {{ api_base }}/api/gemini -H 'Content-Type: application/json' \
  -d '{"text": "Explain what a blueprint is in Flask", "prompt": "Answer in two sentences."}'
curl -b jar -X POST {{ api_base }}/api/groq/chat -H 'Content-Type: application/json' \
  -d '{"messages": [{"role": "user", "content": "Hello"}]}'

GET /api/gemini/health and GET /api/groq/health tell you whether the provider is reachable.

{% endcall %} {% call qa("How does AI grading work? (" ~ kit.roles.staff.label ~ ")") %}

Staff send a batch of submissions to POST /api/gemini/summarize-submissions as form fields (id_0, type_0, text_0 or file_0, then id_1, and so on) and get a summary of each. It uses the same Gemini key as the chat. If AI chatbot is off, turning on AI grading still serves Gemini.

{% endcall %} {% endcall %} {% call section("code", "Running code", "code-runner") %} {% call qa("How do I run Python or JavaScript?") %} 
curl -b jar -X POST {{ api_base }}/run/python -H 'Content-Type: application/json' \
  -d '{"code": "print(2 + 2)"}'
curl -b jar -X POST {{ api_base }}/run/javascript -H 'Content-Type: application/json' \
  -d '{"code": "console.log(2 + 2)"}'

You must be signed in. On a public server the code runs in a separate locked-down container (code_runner), never in the web server, and is stopped if it runs too long. Empty code answers 400.

{% endcall %} {% endcall %} {% call section("games", "Games", "game-engine") %} {% call qa("How do the AI characters (NPCs) work?") %}

POST /api/ainpc/prompt with {"prompt": "...", "session_id": "abc", "npc_type": "wizard"} returns the character's reply and remembers the conversation for that session_id. npc_type is one of history, merchant, guard, wizard, innkeeper or default. POST /api/ainpc/greeting starts over with a greeting, POST /api/ainpc/reset clears the memory, and GET /api/ainpc/test checks the AI is configured.

{% endcall %} {% call qa("How do I save a player's progress?") %}

A signed-in player's game profile is one JSON document: GET /api/profile/game loads it (404 if there is none yet), and POST or PUT saves it.

{% endcall %} {% call qa("How do leaderboards work?") %}

GET /api/dynamic/leaderboard?gameName=pong&limit=10 lists scores. A signed-in player adds one with POST /api/dynamic/leaderboard and {"payload": {"score": 120, "gameName": "pong"}}. /api/events/ELEMENTARY_LEADERBOARD works the same way for the elementary board, and a signed-in person can remove an entry from it with DELETE /api/events/ELEMENTARY_LEADERBOARD/<id>.

{% endcall %} {% endcall %} {% call section("analytics", "Analytics and skills", "analytics") %} {% call qa("What is a skill passport?") %}

GET /api/user/skill-passport returns your current skills and your history. POST /api/user/skill-snapshot records a new snapshot. An admin can read anyone's with GET /api/admin/skill-passport/<user id>.

{% endcall %} {% call qa("How do I see someone's GitHub activity?") %}

GET /api/analytics/github/user (and /commits, /prs, /issues, /issue_comments) reads the signed-in person's public GitHub activity. Staff can read an organization with /api/analytics/github/org/<name>/repos and /users, and admins can read any person's commits and issues. These need GITHUB_TOKEN set in .env; without it they answer that the token is not set.

{% endcall %} {% endcall %} {% call section("study", "Assignments and study tracking", "assignments") %} {% call qa("How do I track what someone has studied?") %} 
curl -X POST {{ api_base }}/api/study -H 'Content-Type: application/json' \
  -d '{"topic": "Flask", "subtopic": "Blueprints", "studied": true, "timestamp": "2026-11-22T10:00:00Z"}'
curl {{ api_base }}/api/study/stats

GET /api/study lists records, and DELETE /api/study/<id> removes one of yours. Anyone can use it today; whether it should need a sign-in is still undecided (it is the unreviewed group on the Permissions page).

{% endcall %} {% endcall %} {% call section("examples", "Teaching examples", "examples") %} {% call qa("What are the jokes, students and congrats endpoints?") %}

Small practice APIs with no real data, for learning how a REST API behaves: GET /api/jokes, /api/jokes/random, /api/jokes/count, GET /api/students, /api/student/john and GET /api/congrats are open to anyone. Adding or rating a joke needs a sign-in.

{% endcall %} {% endcall %} {% call section("elsewhere", "Features this backend does not serve") %} {% call qa("Where are lessons, calendar, hall pass, finance simulation, resume and face recognition?") %}

They have no code in this backend. The Pages site and the Spring backend serve them, and this backend only knows whether each is switched on (GET /api/kit). The same goes for Kasm virtual desktops, which this backend no longer has any code for.

{% endcall %} {% endcall %} {% call section("run", "Running it") %} {% call qa("How do I start it on my own computer?") %} 
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
cp .env.example .env            # set ORG_NAME and, for a public server, the secrets
python scripts/db_init.py       # creates the tables and one account per role
python main.py                  # http://localhost:8587

In development an unset password is 123Qwerty!. With Docker, copy .env.example to .env and run docker compose up -d --build; the first boot creates the database. Restart the server after you change Python code.

{% endcall %} {% call qa("What must I set before going public?") %}

Set IS_PRODUCTION=true, which then requires SECRET_KEY, ADMIN_PASSWORD and DEFAULT_PASSWORD; list your website under CORS; put nginx in front (a template is in deploy/); and optionally limit sign-ups to your email domains. The README has the full checklist.

{% endcall %} {% call qa("How do I check that everything is wired up?") %}

python -m features --list shows the kits and features, python -m permissions --check checks the permission file against the routes, and python -m pytest tests runs the tests.
