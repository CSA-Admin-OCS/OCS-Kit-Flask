{% endcall %} {% call section("The backend image: startup and hardening") %}

entrypoint.sh runs first. It makes sure there is a SECRET_KEY (production refuses to start without one; development generates a random one per container start, so logins reset), creates the instance/ folders, copies the default profile picture back if a fresh mount hid it, and initializes the database if there is none (or if DB_INIT=true). Then it hands over to gunicorn.

The image is python:3.12-slim with no compiler, git or Node. It runs as a non-root user (uid 1000); the code is owned by root and read-only, and only instance/ is writable. So a bind-mounted ./instance must be writable by uid 1000. Its health check fetches /login every 30 seconds, after 90 seconds of grace.

{% endcall %} {% call section("Isolation of submitted code") %}

In production the backend never runs submitted code itself: it posts it to the runner (CODE_RUNNER=remote, which the image sets, and production mode forces). The runner is a separate Alpine container with a non-root user, with all Linux capabilities dropped, 512 MB of memory, one CPU and at most 128 processes. Each run writes the code to a temporary file, runs it with a 5 second limit and a stripped environment (only HOME and PATH) in /tmp, and deletes the file.

Not covered: the compose file does not cut the runner off from the network, so submitted code can make outbound connections. If that matters, add a network policy or network_mode restrictions. And the code routes need a sign-in, so who may run code is a permissions question, not only a sandbox one.

{% endcall %} {{ topic("In front") }} {% call section("nginx and HTTPS") %}

deploy/nginx.conf.template proxies flask.<your domain> to the backend and sends /socket.io/ traffic to the socket service. Fill it in and let certbot add HTTPS:

{% call code() %}export SITE_DOMAIN=example.org FLASK_PORT=8587 SOCKET_PORT=8500 envsubst '${SITE_DOMAIN} ${FLASK_PORT} ${SOCKET_PORT}' < deploy/nginx.conf.template > /etc/nginx/sites-available/flask sudo ln -s /etc/nginx/sites-available/flask /etc/nginx/sites-enabled/flask sudo nginx -t && sudo systemctl reload nginx sudo certbot --nginx -d flask.$SITE_DOMAIN{% endcall %}

Name the variables explicitly in envsubst so nginx's own $variables are left alone. Do not add CORS headers in nginx: the backend sends them, and two copies make browsers reject the answer. deploy/socket-nginx.conf.template serves the socket service on its own hostname instead, if that is preferred.

{% endcall %} {{ topic("Before going live") }} {% call section("Production settings") %}
  1. IS_PRODUCTION=true. The backend then refuses to start without SECRET_KEY, ADMIN_PASSWORD and DEFAULT_PASSWORD, and sends the token cookie Secure, HttpOnly and cross-site.
  2. A long random SECRET_KEY (python -c "import secrets; print(secrets.token_hex(32))"), the same for every worker.
  3. CORS_ORIGINS to the website's origin or origins, or add them on the CORS page afterwards. COOKIE_DOMAIN if the website and backend are on different subdomains of one domain.
  4. Optionally ALLOWED_EMAIL_DOMAINS to limit sign-ups.
  5. nginx with HTTPS, as above, and rate limiting on the sign-in routes, because the backend has none.
  6. MySQL: DB_ENDPOINT, DB_USERNAME, DB_PASSWORD, and DB_INIT=true for the first boot only, then remove it, or the next restart destroys the database.
  7. Back up ./instance and the MySQL database; the API export does not carry the admin settings (see {{ ref('data') }}).
  8. Run through {{ ref('permissions') }}: retire the unreviewed requests that do not belong open.
{% endcall %} {{ topic("Several workers") }} {% call section("Running several worker processes") %}

Each gunicorn worker is its own process with its own memory and its own database connections. That has consequences, all of them deliberate or documented:

  • Admin changes are read from the database on each request (features, permissions, CORS, roles), so every worker agrees at once. See {{ ref('big-picture') }}.
  • Settings from the environment are read once per process: change .env and restart. The same goes for which features the environment selects.
  • Memory-only state is per worker: the spent password-reset tokens (a token is refused only by the worker that accepted it), and the AI characters' conversations (a conversation continues only if the next call lands on the same worker).
  • SQLite is not suited: it allows one writer at a time. Use MySQL.
  • The socket service is a single process, so its players and scores are one shared list, lost on restart.
