Both are signed with SECRET_KEY, which every worker must share: a token signed by one worker has to be accepted by the others. In development an unset key becomes a random one at startup, so a restart signs everyone out; in production the backend refuses to start without one.

{% endcall %} {% call section("Identifying the caller") %}

identify() in api/authorize.py is the one place. It tries, in order: the session, then the token cookie, then an Authorization header (either Bearer <token> or the bare token). For a token it checks that the account still exists and that the token's version matches the account's current one (a session gets the same check when Flask-Login loads it). It answers 401 with a message for a missing, invalid, expired or outdated token, and 500 if decoding fails some other way. Both the permission check and the @token_required decorator call it, so they can never disagree about who the caller is. A caller identified by the session is also available as flask_login.current_user; a token caller only as g.current_user.

The website and the backend are usually on different sites, and the browser only sends the cookie to the backend if it is SameSite=None, which browsers allow only together with Secure. If they share a parent domain, set COOKIE_DOMAIN to it (for example .example.org). The session cookie uses Flask's own defaults in both modes; only the token cookie gets the production settings above.

{% endcall %} {{ topic("Passwords") }} {% call section("Password storage and rules") %}

Only a hash is stored: pbkdf2:sha256 with a 10-character salt, from Werkzeug. A new password must have at least 8 characters, an uppercase letter, a lowercase letter, a number and one of ` ~ ! @ # $ % ^ & * ( ); anything weaker is refused with a 400 and that sentence. The same rule is used by the Spring backend and the website. An already-hashed value is accepted as it is, which is how a backup restore and the bulk import keep passwords working.

{% endcall %} {% call section("Password change and sessions") %}

Each account has a token_version number. It is put inside every session and token when they are created, and checked every time they are used. Setting a different password adds one to it, so every older session and token stops matching and is refused. Setting the same hash again (a restore, an idempotent import) changes nothing, so it does not sign anyone out by accident. This is the only way to revoke a token before it expires, since tokens are not stored on the server.

{% endcall %} {{ topic("Getting an account") }} {% call section("Sign-up and guest accounts") %}

POST /api/user is open to anyone. It needs a name and a uid of at least two characters, a password that follows the rule, and optionally an email, an organization and a class. The new account gets the sign-up role of the current kit (member in every built-in kit). If ALLOWED_EMAIL_DOMAINS is set, an email outside those domains is refused. POST /api/user/guest makes a guest account named Guest_<uid> from just a username and a password, with placeholder email, student id and organization.

{% endcall %} {% call section("Password reset") %}

Two ways. An admin uses the Reset Password button in User Management, which sets the account's password to DEFAULT_PASSWORD (POST /users/reset_password/<int:user_id>), and the person should change it at once. A person resets their own through the website: the Spring backend issues a short-lived, signed reset token, and the website sends it with the new password to POST /api/reset-password. This backend verifies the token's signature (with RESET_TOKEN_SECRET, shared with Spring) and expiry itself, without calling Spring, and rejects a token it has already accepted.

A limit to know: "already accepted" is remembered in the memory of the worker that accepted it, so a restart or a different worker forgets it; the token still expires on its own. If RESET_TOKEN_SECRET is unset the endpoint is closed.

{% endcall %} {{ topic("Leaving, and what is not covered") }} {% call section("Signing out") %}

On the admin pages GET /logout ends the session. For the API, DELETE /api/authenticate sends back an already-expired token cookie so the browser drops it. Neither revokes anything on the server: a token someone copied still works until it expires or the password changes. If an account's token may have leaked, change its password.

{% endcall %} {% call section("Limits of protection") %}
  • Guessing passwords. There is no rate limit and no lockout. Add one in nginx (limit_req) for the sign-in routes.
  • A second factor. There is none.
  • Suspending an account. An account is always active; the way to stop one is to delete it (and an account that owns records cannot be deleted until they are reassigned).
  • A stolen token. See above: change the password.

What it does protect: stored passwords are hashed, the token cookie carries the production flags, every request goes through the permission check, and password hashes are never returned by the general API (only the admin-only backup export carries them, so a backup can be restored).
