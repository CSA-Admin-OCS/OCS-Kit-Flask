{% extends "jumpstart/layout.html" %} {% from "jumpstart/macros.html" import short, section, topic, code, files, ref with context %} {% block content %} {% call short() %} Locate the symptom, read its meaning and apply the corrective action. Most are one of three things: a feature that is off, a request that is not allowed, or a setting that needs a restart. The status code identifies which step refused the request; see {{ ref('request-life') }}. {% endcall %} {{ topic("Requests that are refused") }} {% call section("Route answers 404") %}

Either the route is wrong, or its feature is off: a disabled feature answers 404 to everyone, with an HTML page. Check GET /api/kit for the feature in features, or the live table in {{ ref('kits') }}. If an admin turned it off it stays off across restarts; if the environment was expected to turn it on, a stored kit or override wins over KIT and FEATURES (kit_source says admin).

{% endcall %} {% call section("A new route answers 403 \"is not in permissions.json\"") %}

It is working as designed: a request in no list is refused for everyone. Add the exact entry the message names to permissions.json at the level that fits and restart. See {{ ref('extend') }} and {{ ref('permissions-file') }}.

{% endcall %} {% call section("Works with curl but the website receives 401") %}

The cookie is not being sent. Check, in this order: the website's fetch uses credentials: "include"; the backend is on HTTPS in production, because the token cookie is Secure; COOKIE_DOMAIN is set if the website and backend are on sibling subdomains; and the CORS list allows the website's origin. Then look at the response headers of the sign-in call for a Set-Cookie. See {{ ref('sign-in') }}.

{% endcall %} {% call section("CORS error in the browser") %}

The origin is not allowed. Compare it character for character with the CORS page: scheme (http or https), host and port all matter, and a trailing slash makes it a different string. A preflight that fails shows as a CORS error even when the real request would have worked. Remember a refusal such as a 401 also carries the headers, so a CORS error after a successful sign-in usually means the origin, not the login. If two Access-Control-Allow-Origin headers arrive, nginx is adding its own; remove them. See {{ ref('cors') }}.

{% endcall %} {% call section("Request still refused after being made more open") %}

The route has a check of its own (@token_required(...) or is_admin()) that the page cannot loosen. The page can always make a request stricter. See {{ ref('permissions') }}.

{% endcall %} {% call section("Everything answers 503 \"Permissions cannot be read right now\"") %}

The database that holds admins' saved settings cannot be read, so the system fails closed. Look at the backend log (one error per outage) and fix the database connection; it recovers on its own with the next request that can read.

{% endcall %} {{ topic("Starting up") }} {% call section("Refusal to start in production") %}

With IS_PRODUCTION=true it needs SECRET_KEY, ADMIN_PASSWORD and DEFAULT_PASSWORD, and says which one is missing. Every password must also follow the rule: 8 or more characters with an uppercase letter, a lowercase letter, a number and one of ` ~ ! @ # $ % ^ & * ( ). An unknown KIT or FEATURES id also stops it, with the list of valid ones, and so does a malformed pattern in CORS_ORIGINS.

{% endcall %} {% call section("Changes to .env have no effect") %}

Settings are read once at startup: restart. And some things are not settings: if an admin applied a kit or changed a feature, permission, CORS list or role on a page, that is stored in the database and wins over the file.

{% endcall %} {% call section("Accounts signed out at every restart") %}

SECRET_KEY is unset, so a random one is made on each start in development and the old cookies no longer verify. Put a fixed one in .env. In Docker, the entrypoint generates one per container start for the same reason.

{% endcall %} {% call section("Docker: write failures or an unhealthy container") %}

The backend runs as uid 1000 and may only write to instance/, so the host's ./instance folder must be writable by that user (chown -R 1000:1000 instance). The health check fetches /login and allows 90 seconds to start; see why it fails with docker compose logs -f web.

{% endcall %} {% call section("New template with old behaviour") %}

The development server reloads templates but not Python. Restart python main.py after changing code.

{% endcall %} {{ topic("Things that look broken but are not") }} {% call section("Only the core features work") %}

That is degraded mode: the stored kit and overrides could not be read, so only always-on features run, rather than guess. GET /api/kit shows degraded: true and the home page says so. Fix the database; it recovers by itself. See {{ ref('kits') }}.

{% endcall %} {% call section("A user or role cannot be deleted (409)") %}

A user who still owns records (posts, classrooms) is kept and the answer says so; reassign or delete those first. An admin cannot delete their own account (400). A role that accounts still hold cannot be deleted until they have another.

{% endcall %} {% call section("Password refused (400)") %}

It breaks the password rule, quoted in the answer. The same rule applies on sign-up, on profile changes and on seeded accounts in .env.

{% endcall %} {% call section("The AI or the code runner does not answer") %}

For the AI, check the key: GET /api/gemini/health and GET /api/groq/health say whether the provider is reachable, and a missing GEMINI_API_KEY or GROQ_API_KEY turns that integration off. For the code runner, "could not connect" (502) means the code_runner container is not running or RUNNER_PORT does not match; "timed out" (504) means the code ran over 5 seconds. In development the code runs locally unless CODE_RUNNER=remote.

{% endcall %} {{ topic("Getting back in") }} {% call section("Lost admin password, or no admin remains") %}

If another admin exists, they can reset the password in User Management or give the role to the locked-out account on the Roles page. If not, run this once on the server, in the repository folder with the virtual environment active (it uses your .env, so it reaches the real database; make a backup first):

{% call code() %}python - <<'PY' from main import app, db from model.user import User with app.app_context(): user = User.query.filter_by(_uid='admin').first() # the account to recover user.set_password('ANewPassw0rd!') # must follow the password rule; signs it out everywhere user.role = 'Admin' # the stored admin role name db.session.commit() PY{% endcall %}

The admin role is always L1, so an account with that role always has full power; there is no way to lose the ability to administer except by having no account with it. Nothing in a saved setting can lock admins out, because the sign-in routes and the admin pages are pinned.

{% endcall %} {% call section("Identifying the step that refused") %}

Match the status to the step in {{ ref('request-life') }}: a 404 HTML page is the feature gate or no route; a 403 whose message says "not in permissions.json" or names a level is the permission check; a 401 or a redirect to /login is identification; a 400, 409 or a 403 with a short message from inside a record rule is the route; and CORS headers missing on a response is the origin check, which runs last. The log has a warning for each request that is in no list, and an error when the saved settings cannot be read.
