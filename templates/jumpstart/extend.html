{% extends "jumpstart/layout.html" %} {% from "jumpstart/macros.html" import short, section, topic, code, files, ref with context %} {% block content %} {% call short() %} Adding a route means four things: the function, an entry in permissions.json, a Q&A section if its feature is new to the guide, and a test. The system is built so that forgetting one fails loudly and says what to add. Adding a whole feature adds the catalog entry and, if it has settings or tables, a few more places. {% endcall %} {{ topic("A route") }} {% call section("Adding a route") %}

A blueprint is a module in api/. Using Flask-RESTful, as most of this backend does:

{% call code() %}# api/greeting.py from flask import Blueprint, g from flask_restful import Api, Resource from api.authorize import token_required greeting_api = Blueprint('greeting_api', __name__, url_prefix='/api') api = Api(greeting_api) class Greeting(Resource): @token_required() # identifies the caller and sets g.current_user def get(self): return {'message': f'Hello {g.current_user.name}'} api.add_resource(Greeting, '/greeting'){% endcall %}

@token_required() with no argument accepts any signed-in account; @token_required(roles.admin_role()) asks for the admin level. For a rule about one record (only the caller's own), test it in the function with g.current_user.is_admin() and the record's owner.

{% endcall %} {% call section("Choosing a level") %}

Ask who should be able to make the request, then take the lowest level that fits: public for something anyone may do on purpose (sign-up, a public example), member for any signed-in account, staff for day-to-day work, admin for settings and other people's data. If the right level is not yet known, unreviewed keeps it open and visible on the to-do list, but prefer deciding. The format is in {{ ref('permissions-file') }}.

{% endcall %} {{ topic("Other additions") }} {% call section("Adding a database table") %}

Write the model in model/ and list its module under the feature's flask.models in the catalog, so it is always imported and its table always exists. If the data should survive a migration, add it to the migrated set in api/data_export_import_api.py and both transfer scripts. Remember there are no migration files: on a server that holds data, a schema change goes through export, db_init.py and restore (see {{ ref('data') }}).

{% endcall %} {% call section("Adding a setting") %}

Read it from the environment in __init__.py (with a safe default, and failing at startup if production needs it and it is missing), document it in .env.example with a comment, and add it to the table in {{ ref('settings') }}. A test compares the settings the code reads with that table in both directions, so an undocumented setting fails the tests, and so does a documented one that nothing reads. If a feature needs it, also list it in the feature's setup.settings in the catalog so the admin payload can report whether it is configured.

{% endcall %} {% call section("Adding an admin page") %}

Write a route with @admin_page_required (or @staff_page_required) that renders a template extending layouts/base.html, with its API next to it using @token_required(...). Add the page and API to permissions.json; list the pinned ones if a wrong click on them could lock people out. Add an admin_links entry to the feature in the catalog, with a "group" such as "Web Security" to put it in a sub-menu. The page then appears in the Data menu and on the home page for exactly the people who may open it.

{% endcall %} {% call section("Adding a complete feature") %}
  1. Add the feature to the canonical catalog first (id, name, category, labels, description and a setup guide), since the catalog is shared with the website and Spring, and add it to the kit presets that should include it.
  2. Copy everything except the flask blocks verbatim into this repository's kits/catalog.json.
  3. Write the blueprint and models, then fill the feature's flask block: blueprints, uses_blueprints if it needs another feature's, models, seed, startup, admin_links. The keys are explained in {{ ref('catalog-file') }}.
  4. Add its requests to permissions.json, a section to the Q&A guide, and tests.
  5. Run python -m features --check, python -m permissions --check and python -m pytest tests.
