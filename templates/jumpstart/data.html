{% extends "jumpstart/layout.html" %} {% from "jumpstart/macros.html" import short, section, topic, code, files, ref with context %} {% block content %} {% call short() %} One database (SQLite while developing, MySQL in production) holds accounts, every feature's data and the settings admins changed on the pages. A few folders under instance/ hold uploads and shared files. A backup through the API carries the data but not the admin settings, and rebuilding the database wipes both. {% endcall %} {{ topic("Which database") }} {% call section("Choice of database") %}
  1. If SQLALCHEMY_DATABASE_URI is set, that, whatever it is (meant for tests and unusual setups; the init script cannot back it up, so it asks for ALLOW_NO_BACKUP).
  2. Else if DB_ENDPOINT, DB_USERNAME and DB_PASSWORD are all set: MySQL on port 3306, database user_management, through PyMySQL.
  3. Else SQLite: the file instance/volumes/user_management.db, with the init script keeping a copy beside it as user_management_bak.db.

The folder is created at startup if it is missing (SQLite makes the file but not its folder). Sessions are not in the database: they live in signed cookies, and the backend keeps no server-side session store.

{% endcall %} {{ topic("What is in it") }} {% call section("Tables") %}

Every feature's tables always exist, whatever the kit, because all models are always imported; only the starting data depends on the kit.

AreaTables
People and structureusers, sections, user_sections (who is in which section, and the year), classrooms, classroom_student

The nine admin tables are created at startup if a database from before them lacks them, so an older database keeps working. An *_audit table is the log shown under Recent changes: who changed what, and when.

{% endcall %} {% call section("Account data") %}

The row in users holds the uid, name, email, student id, organization, the role name, the password hash and its token version, the profile-picture file name, class and grade data, and a game profile as JSON. Passwords are never stored in a readable form, and the general API strips the hash from every answer. The organization is stored in the column that was always called _school, so databases from before the rename needed no migration.

{% endcall %} {{ topic("Files") }} {% call section("Storage outside the database") %}
  • instance/uploads/: profile pictures, one folder per uid. At most 5 MB per upload, and only .jpg, .png and .gif. A default picture is kept in instance/uploads/default/.
  • instance/data/: shared files a feature keeps, such as the jokes list.
  • instance/backups/: created when needed, where the init script puts a MySQL dump before it drops anything.

In Docker, ./instance on the host is mounted over the container's instance/, so that folder is what must be backed up. The entrypoint copies the default picture back in when a fresh mount has hidden it.

{% endcall %} {{ topic("Rebuilding and backing up") }} {% call section("The db_init.py script") %}
  1. If the database already has data tables, it warns that all data will be lost and asks (FORCE_YES=true skips the question).
  2. It makes a rollback point: a copy of the SQLite file, or a mysqldump into instance/backups/. If it cannot, it refuses to drop anything unless ALLOW_NO_BACKUP=true.
  3. It drops every table, including the nine admin ones, and creates them all again.
  4. It seeds the enabled features' starting data, and, because the database is empty, creates one account per role (and a few demo accounts and personas).

So a rebuild also forgets the kit an admin applied, every permission, CORS and role change, and their logs. The Docker entrypoint runs it by itself only when there is no SQLite file yet, or when DB_INIT=true is set (needed once for a first MySQL boot).

{% endcall %} {% call section("Export and backup through the API") %}

The admin-only routes under /api/export/ export and import these data types: sections, users, topics, microblogs, posts, classrooms, feedback, study, personas, user personas, leaderboard, elementary leaderboard and skill snapshots (GET /api/export/all, GET /api/export/counts, POST /api/export/import and one pair per type). Users are exported with their password hash so a restore keeps everyone's password; that is why these routes are admin-only.

Not included: the nine admin tables. After restoring into a fresh database, re-apply what admins had set: the kit and feature overrides, permission changes, the CORS list and added roles. If a model was added, add it to the migrated set in api/data_export_import_api.py and to both transfer scripts, or its data is silently lost in a migration.

{% endcall %} {% call section("Moving data and changing the schema") %}

python scripts/db_migrate-prod2sqlite.py pulls everything from a running server (FLASK_BASE_URL) into the local SQLite file through those export routes; python scripts/db_restore-sqlite2prod.py pushes it back. Both reconcile the row counts and exit non-zero if any table did not transfer completely, so do not carry on past a failure (ALLOW_PARTIAL_EXPORT=true exists only to inspect a broken endpoint).

There are no migration files: the schema is created from the models. To change it on a server that holds data: deploy the new code, pull the data locally, run db_init.py on the server, restore. Plan for that when a column is added.

{% endcall %} {% call section("SQLite and MySQL compared") %}

For development, no. In production use MySQL: SQLite allows one writer at a time and the Docker image runs several workers; MySQL also enforces foreign keys, which is why deleting a user who still owns records (posts, classrooms) answers 409 instead of leaving orphaned rows. Times are stored in UTC.
