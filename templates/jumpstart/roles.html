Everything that decides by role asks the tier, in one place, roles.py, so a role an admin adds at L2 really has staff powers. {% endcall %} {{ topic("Roles, tiers and levels") }} {% call section("Role, tier, rank and level") %} {% call code() %}account --has--> role --has--> tier (L1..L4) --gives--> rank (3..0) --compared with--> the level a request needs (admin 3 .. public 0){% endcall %}

The starting tiers come from the order of the three built-in roles (admin, staff, member) in roles.py; the number of tiers is that count plus one, with L4 meaning "signed in, but no more than someone who is not". A level belongs to a request; a tier belongs to a role. See {{ ref('permissions') }} for the levels.

{% endcall %} {% call section("Role storage") %}

The account stores the role's name: Admin, Teacher or User for the built-in ones (the flask.roles map in kits/catalog.json), or whatever an admin typed for a role they added (2 to 20 characters, because the account's column is 20 wide). What people see is a separate label: the kit calls the staff role Teacher, Manager or Editor, and an admin can overwrite any label. Because the stored name never follows the kit, switching kits never rewrites an account. A stored role that is no longer a role (nothing can leave one behind, but an old import might) counts as a member.

Before tiers, every one of these compared role names, so a custom role would have passed the permission check and then been refused by a decorator. Asking one function removes that whole class of bug.

{% endcall %} {% call section("The meaning of @token_required(roles.staff_roles())") %}

The decorators are still written with built-in role names, because that is what the code has always said. meets() reads each built-in name as its level: ('Teacher', 'Admin') means "staff level or stronger", which any role at L2 or L1 satisfies; ('Admin',) means admin level, L1 only. A name that is not a built-in role (a custom one) must match exactly. Notice what this means: if an admin moves the Teacher role down to L4, the name Teacher in a decorator still stands for the staff level, and a Teacher at L4 no longer satisfies it.

{% endcall %} {% call section("Finding a role's tier") %}
  1. The admin role is always L1 and needs no database.
  2. Otherwise the saved tier from the role_setting table, if an admin saved one (a custom role always has one; a built-in role has one only if changed).
  3. Otherwise the starting tier of a built-in role, and L3 for an unknown role.
  4. If the saved roles cannot be read: L4 for everyone but admin, until they can, with one error logged per request. It fails closed.

The saved roles are read once per request and cached for it, and the cache is cleared after every write, so a change is visible to the response that makes it.

{% endcall %} {{ topic("Changing roles safely") }} {% call section("Safeguards against lock-out") %}
  • The admin role is always L1 and cannot be deleted. Asking for another tier is a 400.
  • An admin cannot change their own role (PUT /api/user/role answers 400), so there is always another admin to ask, and the one who is signed in cannot demote themselves.
  • A role that accounts still hold cannot be deleted (409 naming how many). Give them another role first.
  • Role names cannot repeat, even in a different case, and cannot reuse a built-in name.
  • Making a role L1 asks for confirmation on the page, because it grants everything the admin role can do.
  • Every change, and every role given to an account, is logged with who did it (role_audit, shown under Recent changes).
{% endcall %} {% call section("Adding a role, and what each tier grants") %}

On the Roles page, or POST /api/roles with {"name": "Coach", "label": "Coach", "tier": 2}; then give it to an account with PUT /api/user/role and {"uid": "ada", "role": "Coach"}. Change a role with PUT /api/roles/<string:role_name> and a label and/or tier, remove one with DELETE /api/roles/<string:role_name> (which, for a built-in role, resets its tier and label), and list them with GET /api/roles. What a tier means in practice:

  • L2 "Coach" opens the user table and sections page, creates classrooms, and reaches every staff-level request. It cannot change features, permissions, CORS or roles.
  • L3 "Helper" is a normal signed-in account.
  • L4 "Observer" can use only what the public can: it can see the home page and the public examples but is refused GET /api/id, which needs a member.
{% endcall %} {% call section("Limits on customizing a role") %}

Because a tier is a position on one scale, and the permission model is "request needs a level, caller has a rank". A per-role exception list would be a second dimension on top. The design keeps it to one: pick the tier that fits, and if a request should be more or less open, change its level on the Permissions page, for everyone. If the need arises for "Coaches may do X but Teachers may not", that is a sign to give them different tiers.
