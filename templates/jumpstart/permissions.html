An anonymous caller has rank 0. A signed-in caller has rank 4 - tier: L1 is 3, L2 is 2, L3 is 1 and L4 is 0, so an L4 account may do no more than someone who is not signed in. The request is allowed when rank >= level's rank. These counts are the file's; the Permissions page shows the live ones including admins' changes. See {{ ref('roles') }} for where the tier comes from.

{% endcall %} {% call section("Refusal of unlisted requests") %}

So that a new route can never be open by accident. If a developer adds a route and forgets to say who may use it, the first call answers 403 with a message naming the exact entry to add. Three things catch it earlier: the app logs a warning at startup listing every route missing from the file, python -m permissions --check lists them and exits non-zero, and the tests fail. The file also may not list a request that no route serves (a stale entry), and may not list the same request twice.

{% endcall %} {% call section("The unreviewed list") %}

When the permission system was added, {{ facts.by_level.unreviewed }} requests were still open to anyone only because they always had been, and the right level for each was a decision rather than a fact. Rather than call them public, which would say someone chose that, they are listed as unreviewed: they behave exactly like public but show in yellow on the Permissions page and in python -m permissions. Retiring one is a one-line move to the level it belongs at, either in the file or from the page.

{% endcall %} {{ topic("Changing it") }} {% call section("Source of a request's level") %}
  1. If the request is pinned in the file, its level is the file's, always. A saved change for it is ignored.
  2. Otherwise, if an admin saved a level for it on the Permissions page, that is its level (stored in permission_override, and logged in permission_audit).
  3. Otherwise the level in permissions.json.
  4. If it is in neither: refused (403). If the saved levels cannot be read: refused (503).

Choosing on the page the level the file already gives is stored as no change, and Reset deletes the saved level. Pinned requests are the login routes and the admin pages of this feature (Permissions, CORS, Roles), so a wrong click cannot lock everyone out.

{% endcall %} {% call section("Limits of making a request more open") %}

Because the file and the page decide who gets as far as the route, and many routes also check for themselves, through @token_required(...) or an is_admin() test inside. That check is a second layer, kept on purpose, and the stricter of the two wins. So the page can always make a request stricter, but can make one more open only where the route has no check of its own. Try setting GET /api/id to public: it still answers 401 to an anonymous caller, because the route insists on a login. The honest fix is in the code: remove the route's own check once the file is the only authority for it.

{% endcall %} {% call section("Request-level and record-level rules") %}

The permission check knows the request and the caller's tier, not the record. "Staff may list classrooms" is a level. "A member may change only their own profile" and "an admin may delete anyone but themselves" need the record, so they are written in the route, using is_admin() and the account's id. The two combine: the check lets the request through, then the route applies the rule about the record.

{% endcall %} {{ topic("Seeing what is allowed") }} {% call section("Determining what a person may do") %}
  • The Permissions page lists every request by feature with its level, and colours it: green decided, yellow unreviewed, red locked.
  • The Roles page shows how many requests each tier may make right now.
  • In code, permissions.may_make(method, route, user) answers for one request and one person. The home page's "Your tools" and the user table's Edit menu are built with it, so they only offer what the viewer may open.
  • python -m permissions prints the counts and the unreviewed list; python -m permissions --check compares the file with the app's routes.
{% endcall %} {% call section("Behaviour when the database is unavailable") %}

It answers 503 "Permissions cannot be read right now" instead of guessing from the file, because a saved change might have made a request stricter and falling back to the file could allow it. Open requests whose level was never changed still cannot be told apart from changed ones without reading, so they answer 503 too until the database is back. Login is pinned and so cannot be changed, but it needs the database anyway.

{% endcall %} {% call section("Adding a request to the file") %}

Put "METHOD /route" (the route as Flask writes it, with <int:id> and the like) under the right level, and run python -m permissions --check. The format is in {{ ref('permissions-file') }} and a full walkthrough is in {{ ref('extend') }}.
