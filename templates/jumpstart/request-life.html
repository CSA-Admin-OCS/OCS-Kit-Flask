Steps 2 and 3 are two before_request hooks. Flask runs them in the order they were registered: the feature gate is registered when the blueprints are, and the permission check is registered at the end of main.py, so the gate always runs first. A request that is refused in either step never reaches your code.

{% endcall %} {% call section("Feature gate and permission check") %}

So a feature that is off answers 404 to everyone, including people who would be refused anyway. Otherwise an anonymous caller would get 401 for a route that, as far as the system is concerned, does not exist, and learn that it does. The gate asks which blueprint the request belongs to and whether any feature that owns that blueprint is on (a few blueprints are shared, like the Gemini routes used by both ai-chatbot and ai-grading). Routes that belong to no feature, the core ones, are never gated.

{% endcall %} {{ topic("The permission check, step by step") }} {% call section("The permission check") %}
  1. Is there anything to guard? A browser's OPTIONS preflight, a request that matched no route, and static files are let through.
  2. Find the level. It builds the request line (GET for HEAD) and reads the level an admin saved for it, else the one in permissions.json (a pinned request ignores any saved change). A request in neither is refused with 403 and a message naming the entry to add. If the saved levels cannot be read it answers 503.
  3. Open levels pass. public and unreviewed go straight to your route, and nobody is identified.
  4. Identify the caller. For an API path: the session cookie, else the token cookie, else an Authorization header. For an admin page: the session only. Nobody found: 401 JSON for the API, a redirect to /login?next=... for a page.
  5. Compare tiers. The caller's rank (from the role's tier) must reach the level, else 403: JSON for the API, an error page for a page.

Which paths count as API paths is data, not code: the api_paths list in permissions.json. See {{ ref('permissions') }} for the model and {{ ref('roles') }} for how a role becomes a rank.

{% endcall %} {% call section("Routes and @token_required") %}

It still needs it when it uses g.current_user. The check identifies the caller only for requests that need a login; an open request (public or unreviewed) is not identified, so a route behind one that reads g.current_user must ask for it itself. The decorator also stays as a second layer: if it asks for more than the file does, the stricter one wins, which is why the Permissions page can always make a request stricter but can only make one more open when its code has no check of its own. Checks about one record (you may change only your own profile) can only be made in the route, where the record is known.

{% endcall %} {{ topic("Your code and the way out") }} {% call section("What a route receives") %}
  • g.current_user: the account, when the request was identified (by the check or by the decorator). The same lookup serves both, in identify() in api/authorize.py.
  • request.url_rule: the route template, such as /api/classrooms/<int:id>.
  • The models in model/, over SQLAlchemy, with the database session of this worker.

Routes answer JSON. Errors raised as Flask HTTPExceptions become JSON when they come from an API resource, and a plain 404 anywhere becomes the HTML "Something Went Wrong" page, because the 404 handler in main.py renders a template for every 404, API or not. Clients should read the status code, not the body, for a 404.

{% endcall %} {% call section("Preflight (OPTIONS) requests") %}

Flask answers OPTIONS itself for every route. The feature gate still applies (a disabled feature's preflight is a 404), the permission check lets it through because a preflight carries no cookies, and the CORS step adds the allowed methods and the headers the browser asked about, if its origin is allowed. See {{ ref('cors') }}.
