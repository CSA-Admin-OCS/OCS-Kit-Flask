{% endcall %} {% call section("Per-request database reads") %}

Because production runs several worker processes (five in the Docker image), and a worker only knows what it has loaded itself. If an admin changed a permission and one worker remembered the old answer, the same request would be allowed on one call and refused on the next. So the settings admins can change are read on each request, a few small queries each, and cached only for the length of that one request. The price is a little work per request; the gain is that a change is in force everywhere at once. The {{ ref('request-life') }} chapter shows exactly what is read and when.

{% endcall %} {% call section("Admin pages and the API") %}

The admin pages (user table, sections, Permissions, CORS, Roles) are rendered by this backend as HTML and use the session cookie from the /login form. The website uses the JSON API with the token cookie from POST /api/authenticate. Both go through the same permission check, which tells them apart by path: requests under the configured API paths (/api/ and /run/) get JSON answers, the rest get a redirect to the login page. See {{ ref('sign-in') }}.
