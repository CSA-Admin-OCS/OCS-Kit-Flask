{% extends "jumpstart/layout.html" %} {% from "jumpstart/macros.html" import short, section, topic, code, files, ref with context %} {% block content %} {% call short() %} A browser lets a website call a different website's API only if that API says the website's origin is allowed. The backend keeps one list of allowed origins: the one an admin saved on the CORS page, else CORS_ORIGINS, else the local development sites. It is read on every cross-origin request, so a change applies at once in every worker. {% endcall %} {{ topic("Why it exists") }} {% call section("Origins and browser refusals") %}

An origin is the scheme, host and port of a web page: https://pages.example.org, http://localhost:4500. The site and the backend are normally on different origins. By default a browser stops a page from reading the answer to a request to another origin; the other side opts in by sending Access-Control-Allow-Origin naming the page's origin. This is the browser protecting the person using it, and it is not a way to keep programs out: curl ignores it, which is why permissions are separate. A failed CORS check shows in the browser console as a "CORS error", with the request often having reached the backend and been answered.

{% endcall %} {{ topic("What the backend does") }} {% call section("Response headers") %}

Only when the request has an Origin header (a browser sends it for cross-origin requests) and the origin is allowed:

HeaderValue
Access-Control-Allow-Originthe request's own origin, exactly as sent
Access-Control-Allow-Credentialstrue, so the browser may send and accept cookies
Varyadds Origin, so a cache never serves one site's answer to another
on a preflight only:
Access-Control-Allow-Methods		DELETE, GET, OPTIONS, POST, PUT
on a preflight only:
Access-Control-Allow-Headers		whatever headers the browser said it wanted, sorted

A preflight is the OPTIONS request a browser sends first when a call is not "simple" (JSON, or any cookie, header or method beyond the basics). A request from an origin that is not allowed gets no CORS headers at all, and the browser blocks the page. The headers go on every answer, including a 401, 403 or 404, so the page can read why it was refused. A request with no Origin header (same-site, or not from a browser) gets none, because it needs none.

{% endcall %} {% call section("Origin matching") %}

Exactly, ignoring case: http://localhost:4500 does not match http://localhost:45001 or http://localhost:4500/ (a trailing slash makes it a different string, which is why the page refuses to save one). The one exception is the list in CORS_ORIGINS, which, as it always could, may hold a pattern: an entry with regular-expression characters is matched as a regular expression (case-insensitive, from the start), and * alone means every site. Patterns are checked at startup, so a malformed one stops the app instead of silently never matching. A pattern can only come from .env; the CORS page saves exact origins only.

{% endcall %} {{ topic("The list") }} {% call section("Source and administration of the allowed list") %}
  1. The list an admin saved on the CORS page (PUT /api/cors), kept in the cors_setting table.
  2. Otherwise CORS_ORIGINS, a comma-separated list in .env.
  3. Otherwise the local development sites (localhost and 127.0.0.1, ports 4500 and 4000).

Reset (DELETE /api/cors) forgets the saved list so the setting decides again. Saving an empty list is valid and allows no website. Only exact origins are accepted, at most 100, and the page warns about http:// origins that are not local, because cookies and passwords would cross that connection unencrypted. GET /api/cors shows the list, where it came from, the setting's list and the recent changes. All three requests are admin-only and pinned.

{% endcall %} {% call section("Behaviour when the saved list is unreadable") %}

No cross-origin request is allowed until it can, and the error is logged. That is the safe side: wrongly refusing a website is a visible, fixable outage, while wrongly allowing one is not.

{% endcall %} {{ topic("Around it") }} {% call section("CORS and cookies") %}

No. Cookies are a separate rule: the token cookie must be SameSite=None and Secure to be sent from another site, and COOKIE_DOMAIN lets sites under one parent domain share it. See {{ ref('sign-in') }}. If a call fails with a CORS error and then a 401, fix CORS first, then the cookie.

{% endcall %} {% call section("The socket service and nginx") %}

Not the saved list. The socket service is a separate container that reads CORS_ORIGINS from its environment only, so an origin added on the CORS page does not reach it; put it in .env too. And do not add CORS headers in nginx: the backend already sends them, and two Access-Control-Allow-Origin headers make browsers reject the answer. The nginx template says so.
