{% endcall %} {{ topic("Deciding what is on") }} {% call section("Deciding which features are on") %}
  1. A kit an admin applied at runtime wins. It is stored in the database; its preset applies, then admin overrides. KIT and FEATURES are ignored while it is stored.
  2. Otherwise the environment: KIT picks a preset (unset means everything), FEATURES adjusts it. This is worked out once per process, at startup. Then admin overrides apply.
  3. Admin overrides (one feature on or off) always apply last and win over both.
  4. If the stored kit and overrides cannot be read, only the always-on features run until they can. It does not fall back to the environment, because that would bring back a feature an admin had switched off.

GET /api/kit reports the result, including kit_source (admin, env or default), whether it is customized from the preset, and whether it is degraded.

{% endcall %} {{ topic("What a switch does") }} {% call section("A disabled feature") %}

Every request to one of its blueprints answers 404, including the wrong-method case that would normally be a 405, so it does not reveal itself. Its admin links vanish from the menus. Nothing is deleted: every feature's tables are always created, whatever the kit, because all models are always imported, so turning a feature on again needs no migration and finds its data intact. Blueprints shared by two features (the Gemini routes, used by ai-chatbot and ai-grading) stay on while either is.

{% endcall %} {% call section("Turning a feature on") %}

Its startup functions run (for example the jokes file for examples), and its seed functions run only if the feature's tables are empty, so reference data (the personas for social) is created once and never duplicated by turning a feature off and on. Seed functions never create accounts. Functions that create accounts with known passwords are listed separately (seed_accounts), and only python scripts/db_init.py runs them, on a database with no users.

{% endcall %} {% call section("Changing features and kits at runtime") %}
RequestEffect
GET /api/kit/admineverything in /api/kit, plus each feature's source (kit, env or admin), its setup guide, whether its required settings are set, and the recent changes
PUT /api/kit/admin/features{"features": {"social": false}} sets overrides; unknown ids and disabling core are 400
DELETE /api/kit/admin/features/<feature_id>clears one override, so the kit decides again
PUT /api/kit/admin/kit{"kit": "business"} applies a preset and clears all overrides
DELETE /api/kit/admin/kitforgets the stored kit and overrides, going back to KIT and FEATURES

All are admin-only. A kit switch never touches accounts or data: stored roles, uids and logins stay as they are, and only labels and the role of new sign-ups follow the new kit. Every change is logged in feature_audit with who made it.

{% endcall %} {% call section("Degraded mode") %}

It is what the system does when it cannot read what admins saved (a database failure, as opposed to nothing being saved). GET /api/kit then says degraded: true (the reason is in the admin payload), the home page shows a notice, only always-on features answer, and every attempt to change features answers 503. Every request tries to read again, so it recovers by itself the moment the database answers, and the error is logged once per outage rather than once per request.

{% endcall %} {{ topic("Checking it") }} {% call section("Inspecting the feature setup") %}

python -m features --list prints the kits, the categories and every feature with whether it is on. python -m features --check validates the catalog against the code and exits non-zero on a problem: unknown categories or labels, a blueprint or model that does not import, a blueprint claimed by two features, a blueprint in api/ that no feature lists (so new code cannot skip gating), an admin link that points into another feature's blueprint, and drift from the canonical catalog when that is present.
