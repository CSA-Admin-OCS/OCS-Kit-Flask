test_catalog_matches_code asks the feature checker to import every module the catalog names, and the grading module needs pandas and scikit-learn. Both are listed in requirements.txt, so an environment installed from the current file has them. In one set up earlier, run pip install -r requirements.txt again and the test passes; until then it is the only failure.

{% endcall %} {{ topic("How they are set up") }} {% call section("Shared setup") %}

tests/conftest.py runs before the app is imported:

  • It points SQLALCHEMY_DATABASE_URI at a temporary SQLite file and sets every setting the app reads, to blank or a fixed value, so a developer's .env or a running stack cannot leak in.
  • The kit under test is education with FEATURES=+examples,+kasm,-hallpass,-social, in development mode, with the password 123Qwerty! for every account.
  • The app fixture creates the tables and seeds the three accounts once per session. Their uids are admin, teacher and student in this kit.
  • An automatic fixture clears everything admins can change (feature overrides, the stored kit, permission changes, the CORS list, roles and their logs) before and after every test, so tests do not affect each other.
  • login(app, uid) returns a test client signed in as that account, or anonymous for None.

What the fixture does not clear is accounts and content a test creates: a test that makes a user or a post deletes it afterwards.

Use @pytest.mark.parametrize to try every caller or every input, monkeypatch to change a setting or make something fail, and app.test_request_context(...) to call a function that needs a request without running a route. Test the refusals as carefully as the successes: most of the interesting behaviour in this backend is a no.

{% endcall %} {% call section("Verifying that a test detects defects") %}

A habit rather than a tool: after writing a test, break the code on purpose (flip a comparison, skip a check, make a lookup fail open), run the test, and see it fail, then put the code back. A test that stays green when the code is wrong proves nothing. Several of the suites here were written this way, for example the tier tests fail if the tier is ignored, a decorator goes back to comparing names, or the permission check ignores the tier.

{% endcall %} {% call section("Accuracy of this guide") %}

tests/test_jumpstart.py checks that:

  • every chapter in the contents has a template, renders for anyone, and every link between chapters lands on a real one
  • every file named in a chapter exists in the repository
  • every request marked as a route (GET /api/kit and the like) is one the app really serves, with that method
  • every command marked as a command points at a script or module that exists
  • the settings chapter lists exactly the settings the code reads, the example file declares and the entrypoint uses, in both directions
  • every error message the permissions-file chapter quotes is in the code
  • every test file in tests/ is described in this chapter, and every feature is in the live tables

The tables with numbers (requests per feature, per level, per path) are not written by hand at all: they are computed from the running app each time the page is shown.
